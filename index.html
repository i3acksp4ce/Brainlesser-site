Routing

Capability Routing Table

Intent comes from the conversation; the user does not need to name a capability. Before starting any capability, route to the smallest capability that fully handles the work.

Trigger Route To
Unclear idea, requirement, or plan Discuss
User types discuss or intent is to clarify through conversation Discuss (regular)
User types auto discuss or wants agent-run discussion Discuss (Auto Discuss)
Clear requirement without executable tasks Planner
Clear plan or requirement that needs issue-ready slices Create Issues
Plan, issue draft, or conversation with executable tasks Execute Plan
Bug, test failure, build failure, performance regression, or unexpected behavior Debug Engineer
Engineer hits a bug, test failure, or unexpected behavior during execution Debug Engineer
Caller needs a review gate or quality assessment Review Engineer

Storage

Artifact File Architecture

Artifact files are markdown files stored under .brainlesser/ to hold context, plans, issue drafts, and execution runs. Each type has its own folder with an index.yml lookup file.

.brainlesser/ ├── discuss/ │ ├── index.yml │ ├── 0001-task-filter-sidebar.md │ └── 0002-api-auth.md ├── plans/ │ ├── index.yml │ ├── 0001-task-filter-sidebar.md │ └── 0002-api-auth.md ├── issues/ │ ├── index.yml │ ├── 0001-filter-status-assignee.md │ └── 0002-auth-token-refresh.md └── executions/ ├── index.yml ├── 0001-filter-status-assignee.md └── 0002-auth-token-refresh.md
discuss/Stores Plan-ready briefs from Q&A sessions. Uses write-at-end policy - no file created during active Q&A.
plans/Implementation plan files with hybrid format: human-friendly overview plus agent-executable tasks with issue-ready slices.
issues/Issue draft files as vertical slices with behavior, acceptance criteria, AFK/HITL classification, and dependency info.
executions/Execution run files tracking source readiness, mode selection, engineer dispatch results, and final verification state.
Checkpoints

Checkpoint System

Static identifiers that trace work across Plans, Issues, Execution, Debug, and Review without timestamps or a central registry. Checkpoints do not apply to Discuss.

Format
<source-prefix>-<type><sequence>
Prefix Rules
  • Plan source exists: use plan namespace (e.g. P0001)
  • Issue set without plan: use issue namespace (e.g. I0001)
  • Derive from artifact type and run number every time
  • Never reuse a checkpoint number, even if a section was deleted
Examples
P0001-T01 P0001-I01 P0001-E01 P0001-D01 P0001-R01 I0001-E01

Configuration

Configuration System

Global prompt injection from config.yml, used to load or invoke skills and prompts at the runtime scope. Configuration is not a capability; it shapes how every capability runs.

config.yml Schema
prompts: artifacts: "use skill /style-writer-en for writing artifacts" conversation: "use skill /yayer for every conversation" engineer: "" review: ""
  • Missing required key is a blocker
  • Values must be strings; non-string is a blocker
  • Empty string means no injection; skip silently
  • Ignore unknown keys but do not expose as supported schema
  • config.yml is the only source of truth - no defaults or fallbacks
Prompt Load Order
  1. Read config.yml from the Brainlesser skill root
  2. Validate the required schema
  3. Load or invoke prompts.artifacts
  4. Load or invoke prompts.conversation
  5. Detect the selected capability using Capability Routing
  6. If dispatching Solo/Squad/Debug: load prompts.engineer
  7. If dispatching Review: load prompts.review
Prompt Priority (highest first)
  • 1
    System, tool, workspace safety rules
    Always wins
  • 2
    Brainlesser core contract
    English artifact rule, storage, approvals, verification
  • 3
    Capability-specific rules
    Per-workflow constraints
  • 4
    Prompt injection from config
    config.yml referenced prompts
  • 5
    User wording / style preferences
    Lowest priority
Prompt Scope
  • artifacts controls writing style for artifact files only. Must not change output structure or artifact language.
  • conversation controls style of all user-facing terminal output: questions, recommendations, reasons, completion and blocker messages.
  • engineer applies to Solo Engineer, Squad Engineer, and Debug Engineer.
  • review applies to Review Engineer. May define review behavior or quality reviewer helper.
Artifacts

Artifact File Management

The main agent decides whether an artifact update must be written immediately or can be batched. Subagents do not write artifacts.

Write Now

State-changing updates that must not be lost:

  • New artifact file
  • Status change
  • User approval or rejection
  • Blocker or blocker resolution
  • High-risk decision
  • Important terminology or scope decision
  • Failure, paused, cancelled, or completed state
  • Source or checkpoint mismatch, resume, or supersede decision
Batch

Context accumulation without state change:

  • Question Log entries
  • Intermediate notes
  • Minor findings
  • Progress summary
  • Repeated context that does not change a decision
  • Dispatch details waiting for the final result of the same checkpoint
Flush Before

Flush the batch before these events:

  • Changing capability
  • Handing off to Planner, Create Issues, Execute Plan, an Engineer, or Review Engineer
  • Asking for user approval from the latest artifact
  • Summarizing completion
  • Context grows long enough that important details may be forgotten
Discuss Override: Write-at-End Policy
Discuss uses a write-at-end policy instead of the Batch Update Policy. Do not create a discussion file or update discuss/index.yml during Q&A. Write the discussion file and update the index once at Finalize or when the user asks to pause. Conversation history is the source of truth while Q&A is active, so persisting every Q&A pair is unnecessary. This override applies only to Discuss - all other capabilities still use the main Batch Update Policy.

Verification

Pre-Delivery Verification Checklist

Before handing the run back to the user, verify every item below. Fix failures. Report unresolved limitations.

1 Configuration
config.yml read and validated per Required Schema
Prompt load order followed per Prompt Load Order
Prompt scope respected per Prompt Scope
Conflict order applied per Prompt Priority
2 Routing
Intent detected from conversation per Capability Routing
Smallest fitting capability chosen per Capability Routing
Failure routed to Debug Engineer before any fix per Capability Routing
3 Artifact Files
Storage layout respected per Artifact File Management
Batch policy applied per Batch Update Policy
Discuss write-at-end policy respected per Discuss Override
index.yml updates limited to creation, status, source, mode, or path changes
4 Checkpoints
Checkpoint format followed per Format specification
Canonical labels written per Canonical Labels
Duplicate checkpoint policy honored
5 Capability Handoff
Active capability loaded per Capabilities
Engineer Contract loaded for any Engineer dispatch
Test-Driven Development principle loaded when the run applies it
